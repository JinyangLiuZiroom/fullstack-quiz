## 2. 核心概念一：浏览器渲染流程（从输入 URL 到看到页面）

```
URL 输入
  ↓ DNS 解析（域名 → IP）
  ↓ 建立 TCP 连接 + TLS（HTTPS）
  ↓ 服务器返回 HTML
  ↓ 解析 HTML 生成 DOM 树
  ↓ 解析 CSS 生成 CSSOM 树
  ↓ 合成 渲染树 (Render Tree)
  ↓ 布局 (Layout/Reflow)：算每个元素的位置和大小
  ↓ 绘制 (Paint)：填像素
  ↓ 合成 (Composite)：交 GPU 上屏
```

**关键认知**：
- **JS 会阻塞解析**：`<script>` 默认同步执行，会卡住 HTML 解析。放底部或加 `defer`/`async` 解决。
- **改了布局属性（width/top）触发 Reflow（重排）**，开销大；**只改颜色触发 Repaint（重绘）**；**只改 transform/opacity 走 Composite（合成）**，最快。动画优先用 `transform`/`opacity`。

> 性能口诀：**能用 transform/opacity 做动画就别改 width/left**，避免频繁重排。

## 3. 核心概念二：事件循环（Event Loop）⭐最重要

JS 是**单线程**，但浏览器是多线程的（网络、渲染、定时器各一条线程）。「单线程执行」靠**事件循环**调度。

### 3.1 宏任务 vs 微任务

| 类型 | 常见成员 | 执行时机 |
|---|---|---|
| **宏任务 (macrotask)** | `setTimeout`/`setInterval`、I/O、UI 渲染、`requestAnimationFrame` | 每轮循环取一个 |
| **微任务 (microtask)** | `Promise.then`/`catch`/`finally`、`queueMicrotask`、`MutationObserver` | **当前宏任务结束后、下一宏任务前，全部清空** |

### 3.2 执行顺序规则（背下来）

1. 执行当前同步代码（算一个宏任务）
2. 同步代码结束 → **清空所有微任务**（一个不留）
3. 取下一个宏任务 → 重复 1-2
4. 宏任务之间浏览器可能**渲染一次**

### 3.3 经典题

```js
console.log('1')                  // 同步，先打

setTimeout(() => console.log('2'), 0)   // 宏任务，排队

Promise.resolve()
  .then(() => console.log('3'))   // 微任务
  .then(() => console.log('4'))   // 微任务（链上，接着清）

console.log('5')                  // 同步

// 输出顺序：1 5 3 4 2
```

**为什么**：同步 `1`、`5` 先打；本轮宏任务结束，清空微任务 `3`、`4`；再下一个宏任务打 `2`。

> ⚠️ `setTimeout(fn, 0)` **不是 0 毫秒执行**，而是「最快排到下一轮宏任务」，必然晚于本轮所有微任务。

### 3.4 async/await 的本质

`await` 后面的代码，等价于 `.then` 里的回调，**属于微任务**：

```js
async function f() {
  console.log('a')
  await Promise.resolve()   // 到这里让出，后面变微任务
  console.log('b')          // 微任务
}
f()
console.log('c')
// 输出：a c b
```

## 4. 核心概念三：浏览器存储

| 存储 | 容量 | 生命周期 | 是否随请求发到服务器 | 典型用途 |
|---|---|---|---|---|
| **cookie** | 约 4KB | 可设过期时间 | **每次 HTTP 请求自动带**（同域） | 登录 session、服务端鉴权 |
| **localStorage** | 约 5MB | 永久（手动清） | 否 | 主题、token、长期偏好 |
| **sessionStorage** | 约 5MB | 标签页关即清 | 否 | 单页临时状态 |
| **IndexedDB** | 几百 MB+ | 永久 | 否 | 离线数据、大结构存储 |

```js
// cookie（前端只能读非 HttpOnly 的）
document.cookie = 'token=abc; path=/; max-age=3600'

// localStorage
localStorage.setItem('theme', 'dark')
localStorage.getItem('theme')      // 'dark'
localStorage.removeItem('theme')

// sessionStorage（用法同 localStorage，关页即失）
sessionStorage.setItem('draft', '...')
```

> **安全点**：登录 token 别放 localStorage 被 XSS 轻易偷走；敏感鉴权用 **HttpOnly cookie**（JS 读不到，自动随请求带）。这是安全基础，详见模块十二安全篇。

## 5. 核心概念四：URL 与编码

```
https://user:pass@sub.example.com:8080/path/page?query=1#hash
└─┬─┘  └──┬──┘ └────────┬────────┘ └┬┘ └────┬────┘ └──┬──┘ └┬─┘
 协议      凭证     host(域名+端口)  端口  路径     query   hash
```

**编码**：URL 里不能直接放中文/空格/特殊字符，要 `encodeURIComponent`：

```js
const q = '前端 开发'
fetch('/search?q=' + encodeURIComponent(q))   // 前端%20开发
// 接收端 decodeURIComponent 还原
```

- `encodeURIComponent`：编码整个参数值（最常用）
- `encodeURI`：编码整串 URL（不编码 `:/?#` 等保留符）

## 6. 核心概念五：同源策略（CORS 的底层原因）

**同源** = 协议 + 域名 + 端口 三者完全相同。不同源的发请求/读 DOM/读存储会被浏览器**拦截**——这就是同源策略，是安全基石。模块四讲的 CORS，本质是「服务器用响应头告诉浏览器：这个跨域请求我允许」。

```js
// 同源示例（与 https://a.com 比）
https://a.com/page        ✅ 同源
https://a.com:8080/page   ❌ 端口不同
http://a.com/page         ❌ 协议不同
https://b.com/page        ❌ 域名不同
```

> 同源策略拦的是「浏览器侧读取响应」。请求其实发出去了，服务器也处理了，只是浏览器不让你 JS 读结果。这点在排错时很关键（看 Network 有响应但代码报错，就是被同源策略拦了）。

## 7. 常见坑与排错表

| # | 现象 | 根因 | 正确做法 |
|---|---|---|---|
| 1 | `setTimeout` 比 `Promise.then` 晚 | 宏任务晚于微任务 | 记住顺序：同步 → 微任务清空 → 宏任务 |
| 2 | 定时器不准（越走越慢） | 单线程被长任务阻塞 | 用 `requestAnimationFrame` 做动画；关键计时用 `Date.now()` 差值 |
| 3 | `await` 后面的代码「没紧跟执行」 | await 后是微任务，会让出线程 | 理解 async 本质就是 .then |
| 4 | 接口返回了但页面没更新 | 在 await 外读了旧值/没触发响应式 | 在 async 函数内拿到结果再赋值给响应式变量 |
| 5 | localStorage 存对象变 `[object Object]` | 直接存对象被 toString | `JSON.stringify` 存，`JSON.parse` 取 |
| 6 | localStorage 抛 QuotaExceeded | 存太大或隐私模式禁写 | 大结构用 IndexedDB；写操作 try/catch |
| 7 | 刷新页面登录态在 localStorage 有、cookie 没有 | 两者生命周期/机制不同 | token 存 localStorage 要自己塞请求头；cookie 自动带但需 HttpOnly |
| 8 | 中文参数请求 400 | 没 encodeURIComponent | 参数值一律编码 |
| 9 | 跨域请求 Network 有响应但代码报错 | 同源策略拦了读取 | 让后端加 CORS 头或用代理（模块四） |
| 10 | 频繁改 width/top 页面卡 | 触发大量重排 | 用 transform/opacity，或批量改（rAF） |
| 11 | `<script>` 放 head 阻塞首屏 | 同步脚本卡解析 | 放 body 底或加 `defer` |
| 12 | sessionStorage 在新标签没数据 | 它是按标签页隔离的 | 跨标签共享用 localStorage |

## 8. 完整实战：用事件循环解释真实 bug

**现象**：提交表单后，先弹「提交成功」，但列表没刷新；过一会儿列表才出现。代码：

```js
async function submit() {
  await api.post('/order', form)
  alert('提交成功')              // ❌ 在 await 后，是微任务，先于渲染
  list.value = await api.get('/orders')  // 又等一个请求
}
```

**问题**：`alert` 在第一个 await 后执行（微任务），此时列表还没拉。用户先看到弹窗，再等列表。

**修法**：先拿数据再提示，且用更轻的 UI 提示替代阻塞的 alert：

```js
async function submit() {
  await api.post('/order', form)
  list.value = await api.get('/orders')   // 先更新数据
  toast('提交成功')                        // 再提示（非阻塞）
}
```

## 9. 最佳实践

1. **异步顺序不确定时，按「同步 → 微任务 → 宏任务」推导**，别靠直觉。
2. **数据更新优先于 UI 提示**，且提示用非阻塞 toast 替代 `alert`。
3. **大对象存 localStorage 先 `JSON.stringify`**，读取 `JSON.parse` 并 try/catch。
4. **敏感 token 用 HttpOnly cookie**，别裸放 localStorage 被 XSS 偷。
5. **动画用 transform/opacity**，避免频繁重排卡顿。
6. **脚本加 `defer` 或放 body 底**，不阻塞首屏解析。
7. **URL 参数一律 `encodeURIComponent`**，防中文/特殊字符出错。
