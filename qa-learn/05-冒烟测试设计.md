# 模块五：冒烟测试设计（完整学习指南）

> **学习目标**：掌握冒烟测试——「最小验证集合，确认系统主链路没断」，能为一个系统快速设计一套冒烟用例，在提测/发版第一关就挡住「根本跑不起来」的版本。
> **适合谁**：不知道提测第一件事该测啥、或花大量时间测细节却发现登录都进不去的同学。
> **学完能做什么**：给任意系统设计 5-15 条冒烟用例，覆盖核心路径最小闭环，秒级判断「这版能不能继续测」。

## 2. 核心概念：冒烟测试是什么

**冒烟测试（Smoke Test）**名字来自硬件：通电看冒不冒烟（不炸就能继续）。软件里 = **核心路径最小验证集合**，确认「主链路通、基本功能没挂」。

特点：
- **快**：几分钟跑完。
- **少**：只覆盖最核心路径（登录、核心 CRUD、关键业务一笔跑通）。
- **门禁作用**：冒烟不过，直接打回，不进详细测试，省全员时间。

> 与回归区别：冒烟是「这版能不能测」的准入；回归是「改了之后老的还好不好」的确认。冒烟是子集且更精简。

### 设计原则

1. 只选**端到端主链路**（用户最重要的那一条路）。
2. 每条用例**独立、必过**，不依赖复杂前置。
3. 覆盖「关键模块 × 关键操作」，不测边界、不测异常细节。

---

## 3. 快速开始：电商系统冒烟用例

```
SMOKE-01 用户能登录（正确账号密码 → 进首页）
SMOKE-02 商品能搜索并进入详情
SMOKE-03 加购 → 下单 → 支付（一笔完整订单）
SMOKE-04 订单能在「我的订单」查到
SMOKE-05 后台能查看订单（管理端主链路）
```

就这 5 条，5 分钟内跑完。任何一条挂 = 本版不可测，打回开发。

---

## 4. 进阶用法

### 4.1 按「关键业务流」而非「模块」设计

冒烟要从**用户视角的一条龙**出发，而不是「每个模块点一下」。例子（内容平台）：
```
发帖 → 审核通过 → 首页能看到 → 评论 → 通知收到
```
这一条龙覆盖了发布、审核、展示、互动、消息五个模块的**主链路**，比「五个模块各点一下」更有价值。

### 4.2 冒烟可自动化

核心冒烟用接口/UI 自动化常驻（模块八 Playwright），每次构建后自动跑，红灯立刻报警。CI 里常作为第一道门禁（模块九）。

### 4.3 冒烟 vs 详细测试比例

| 类型 | 条数 | 耗时 | 目的 |
|---|---|---|---|
| 冒烟 | 5-15 | 分钟级 | 准入，挡不可测版本 |
| 详细功能 | 数十~数百 | 小时级 | 覆盖功能/边界/异常 |
| 回归 | 按影响筛选 | 可变 | 防旧功能坏 |

## 5. 常见坑与排错表

| 现象 | 根因 | 解决 |
|---|---|---|
| 冒烟写了 50 条变详细测试 | 没抓住「最小」 | 只留核心主链路，边界/异常移出 |
| 冒烟过了详细测才发现登录挂 | 冒烟漏了登录 | 登录/入口必在冒烟里 |
| 冒烟依赖复杂前置数据 | 用例不独立 | 每条自包含，用默认/自建数据 |
| 冒烟不自动化，每次手工点 | 效率低 | 核心冒烟自动化常驻 CI |
| 把异常流写进冒烟 | 超范围 | 异常留给详细测试 |
| 冒烟没覆盖关键业务闭环 | 按模块点而非按流 | 用「用户一条龙」设计 |
| 冒烟过了但核心支线挂 | 支线也是核心 | 多系统确认所有核心流都进冒烟 |
| 冒烟标准不统一 | 各人理解不同 | 团队固化冒烟清单 + 准入门槛 |

---

## 6. 完整实战：给你负责的系统定冒烟清单

1. 列出系统的「用户最关键一条龙」（1-3 条业务流）。
2. 拆成 5-15 条独立可执行的冒烟用例。
3. 标注每条的前置与预期（PASS 标准）。
4. 跑一遍，确认分钟级可完成。
5. （进阶）挑核心几条用脚本自动化。

**验收**：拿到清单的人 5 分钟能判断「本版是否可测」；任何一条不过即打回。

---

## 7. 最佳实践

- 冒烟 = 最小核心主链路，快、少、独立。
- 从「用户一条龙业务流」设计，不是「每个模块点一下」。
- 登录/入口必须包含，否则后面全白测。
- 冒烟不过直接打回，是提测/发版的第一道门禁。
- 核心冒烟尽量自动化，纳入 CI 常驻。
- 团队固化冒烟清单，标准统一，不因人而异。
