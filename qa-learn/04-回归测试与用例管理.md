# 模块四：回归测试与用例管理（完整学习指南）

> **学习目标**：理解回归测试的本质——「改了 A，确认 B 没坏」，掌握变更影响分析（哪些老功能要重测）和用例筛选策略，能管理一套可复用的用例集。
> **适合谁**：每次发版全量手工点一遍、或不知道「这次改动要回归哪些」的同学。
> **学完能做什么**：做一次变更影响分析，筛选出精准回归范围，管理用例集（优先级/标签），让回归从「点一天」变「点半小时」。

## 2. 核心概念：什么是回归测试

**回归（Regression）**：软件修改后，原本正常的功能出现新的故障。回归测试就是**重测受影响区域 + 核心功能**，确认没引入新问题。

为什么重要：修一个 bug 改了公共方法，可能悄悄弄坏三个不相关的页面。不回归就上线 = 拆东墙补西墙。

### 变更影响分析（核心技能）

改代码前先想「这次改动会影响谁」：

```
改动：订单导出加了个字段
影响：
  - 订单导出功能本身（必测）
  - 订单列表（若共用 VO，可能字段变化）(测)
  - 订单详情（同 VO？测)
  - 用户模块（无关，不测）
  - 支付流程（无关，不测）
```

影响分析的输入：代码结构（谁调用了改的方法）、需求关联（哪些需求共用这块）、历史 bug（这块以前出过啥问题）。

## 3. 快速开始：做一轮精准回归

场景：修复「优惠券金额算错」的 bug，改了 `CouponCalculator` 类。

1. **直接受影响**：所有调用 `CouponCalculator` 的链路（下单用券、购物车算价、订单详情展示）。
2. **高优先级回归**：满减、折扣、叠加三类券的核销。
3. **冒烟级**：下单主流程还能走通（模块五 冒烟）。
4. **暂不回归**：用户登录、商品搜索（无关联）。

产出回归用例清单（带优先级 P0/P1/P2），只执行相关部分。

## 4. 进阶用法

### 4.1 用例管理与标签

用例集要可筛选，给用例打标签：

```
标签：模块(订单/用户)、类型(单测/接口/功能)、优先级(P0/P1/P2)、层级(冒烟/回归/全量)
```

回归时按「模块=订单 AND 优先级<=P1」筛选，秒级得到范围。

### 4.2 用例设计要素

一条好用例包含：编号、标题、前置条件、步骤、预期结果、优先级、所属模块、是否自动化。

```
ID: ORDER-REG-007
标题: 叠加券下单金额正确
前置: 用户有满100减20 + 9折券各一张
步骤: 加购120元商品 → 结算选两张券 → 提交
预期: 实付 = 120*0.9 - 20 = 88 元，订单状态待支付
优先级: P0
```

### 4.3 自动化回归

手工回归慢且易漏。把稳定、高频的用例自动化（接口自动化优先，见模块二；UI 自动化见模块八），每次提测自动跑，人只补探索性测试。

## 5. 常见坑与排错表

| 现象 | 根因 | 解决 |
|---|---|---|
| 每次全量回归点一天 | 没做影响分析、用例无筛选 | 变更影响分析 + 用例标签筛选 |
| 改了公共方法漏测关联功能 | 影响分析不全 | 用调用链/IDE「find usages」找所有调用方 |
| 回归后还是出了旧功能 bug | 用例集没覆盖该场景 | 补用例 + 复盘为什么漏（用例缺失 vs 执行漏） |
| 用例越积越乱没法维护 | 没结构、没标签 | 统一模板 + 标签 + 定期清理 |
| 自动化用例脆、一跑就红 | 强依赖 UI/环境 | 接口层自动化优先，环境数据自治 |
| 只回归改的那点，忽略间接影响 | 只看直接改动 | 影响分析要含「共用组件/VO/配置」 |
| 优先级不分，重要不重要的都测 | 没分级 | P0 核心必须测，P2 可抽测 |
| 历史 bug 反复出现 | 没把历史 bug 转成回归用例 | 每个修复的 bug 沉淀为回归用例 |

## 6. 完整实战：一次发版回归计划

给定本次发版改动清单（3 个需求 + 2 个 bug 修复），产出：
1. 变更影响分析表（改动 → 受影响模块）。
2. 回归用例筛选（标签筛选结果，含 P0 必测、P1 抽测）。
3. 自动化已覆盖部分（自动跑） + 手工补充部分。
4. 回归报告模板（通过数/失败数/遗留风险）。

**验收**：别人拿到这份计划能直接执行，且范围精准不冗余。

---

## 7. 最佳实践

- 每次变更先做**影响分析**，再决定回归范围，拒绝无脑全量。
- 用例集结构化：统一模板 + 标签（模块/优先级/层级），便于筛选。
- 历史 bug 必须沉淀为回归用例，防止复发。
- 稳定高频用例自动化，人聚焦探索性测试。
- 回归也要分级：P0 核心必过，P2 可抽测，资源紧张时保核心。
- 影响分析输入：代码调用链 + 需求关联 + 历史故障。
