# 模块二：接口测试实战（完整学习指南）

> **学习目标**：掌握接口测试的核心套路——区分 HTTP 状态码和业务 code、构造各类请求、校验响应、用脚本批量测，能独立对一个后端接口做完整验证。

## 2. 核心概念：状态码 vs 业务 code

**最重要的认知**：HTTP 状态码是「传输层」结果，业务 code 是「业务层」结果，两者独立。

```json
// HTTP 200，但业务失败（参数校验没过）
{ "code": 400, "message": "用户名不能为空", "data": null }

// HTTP 400，框架层拒绝（如参数类型不对、缺必填）
// HTTP 500，服务器抛未捕获异常
```

> **真题常考**：很多新人以为「接口返回 200 就是成功了」，其实 200 只是「服务器正常回了响应」，业务可能 `code=400` 失败。接口测试要**同时断言状态码和业务 code**。

### 常见请求类型

| 类型 | Content-Type | 工具里怎么发 |
|---|---|---|
| 查询参数 | `?a=1&b=2` | Params / `@RequestParam` |
| 表单 | `application/x-www-form-urlencoded` | body 选 form |
| JSON | `application/json` | body 选 raw JSON / `@RequestBody` |
| 文件 | `multipart/form-data` | body 选 form-data 加 file |

---

## 3. 快速开始：用 Postman 测一个接口

1. 建请求 `POST http://host/api/users`，Headers 加 `Content-Type: application/json`。
2. Body → raw → JSON：`{"name":"张三","email":"a@b.com"}`。
3. Send，看：
   - Status：`200 OK`（传输成功）
   - Body：`{"code":0,"message":"success","data":1}`（业务成功，data=新 id）
4. 把 name 改成空，Send，断言 `code=400` 且 message 提示 username。

### 用 Python Requests 脚本化（更适合回归）

```python
import requests
base = "http://host/api"

def test_create_ok():
    r = requests.post(f"{base}/users",
                      json={"name": "张三", "email": "a@b.com"})
    assert r.status_code == 200
    assert r.json()["code"] == 0          # 业务成功
    assert r.json()["data"] > 0

def test_create_empty_name():
    r = requests.post(f"{base}/users", json={"name": "", "email": "a@b.com"})
    assert r.status_code == 200
    assert r.json()["code"] == 400        # 业务失败，但 HTTP 仍是 200
```

## 4. 进阶用法

### 4.1 鉴权

```python
# 先登录拿 token，后续带 Authorization 头
login = requests.post(f"{base}/login", json={"u": "x", "p": "y"})
token = login.json()["data"]["token"]
r = requests.get(f"{base}/users/1", headers={"Authorization": f"Bearer {token}"})
```

### 4.2 关联（链路）

下单测试要先有用户、有库存：「创建用户 → 拿 id → 用它下单 → 断言订单归属」。用变量在步骤间传值。

### 4.3 数据库比对（接口测试常需）

接口返回成功，但还要查库确认真写入：`SELECT * FROM t_order WHERE user_id=?`，断言落库正确（防止「响应说成功实际没存」）。

### 4.4 契约测试思路

前后端约定接口字段（OpenAPI/Swagger），测试按契约校验响应结构，字段缺漏立刻发现。

## 5. 常见坑与排错表

| 现象 | 根因 | 解决 |
|---|---|---|
| 断言「200 就过」漏了业务失败 | 没看业务 code | 同时断言 `status_code` 和 `json()["code"]` |
| 401 一直过不去 | token 过期/没带 / 格式错 | 检查 Authorization 头；Bearer 空格 |
| POST JSON 返回 400 | Content-Type 没设 json 或字段错 | 设 `application/json`，对齐字段名 |
| 测了半天才发现环境错 | 测了测试环境当生产 | 环境变量管理 base url |
| 并发测出脏数据 | 用例间共享状态 | 每个用例独立数据 + 后置清理 |
| 依赖顺序导致偶红 | 用例 A 影响用例 B | 用例相互独立，或用 setup/teardown |
| 只测成功不测失败 | 覆盖不全 | 异常/边界/权限都要有用例 |
| 响应慢误判超时 | 超时设太短 | 合理设 timeout，先确认服务正常 |

## 6. 完整实战：覆盖一个用户接口的全部场景

用例集：
- 正常创建（断言 code=0 + 落库）
- 空用户名（断言 code=400）
- 非法邮箱（断言 code=400）
- 未登录调用（断言 401）
- 重复创建同名（按业务断言：允许/不允许）
- 超长字段（断言长度校验）

**验收**：脚本一键跑完，每个用例明确断言「状态码 + 业务 code + 关键字段」，输出通过/失败清单。

---

## 7. 最佳实践

- 接口测试**双重断言**：HTTP 状态码 + 业务 code，缺一不可。
- 用例独立、可重复：自带数据、后置清理，不依赖执行顺序。
- 鉴权 token 统一获取，避免每用例硬编码。
- 关键写操作测完查库确认真落库，不只看响应。
- 用脚本（Requests/Postman Collection Runner）做回归，别每次手工点。
- 按契约（Swagger）校验响应结构，字段变更早发现。
