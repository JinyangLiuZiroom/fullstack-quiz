# 模块一：测试基础与测试金字塔（完整学习指南）

> **学习目标**：建立正确的测试认知——测试不是「点一点」，而是一套分层体系。搞懂测试金字塔（单测/集成/端到端占比），理解质量左移，能判断一个需求该补哪些测试。
> **适合谁**：只做过手工点页面的同学，或不确定「为什么要写单测」「自动化测试值不值得投入」的同学。
> **学完能做什么**：给一个新功能规划测试策略（哪些写单测、哪些做接口测试、哪些留给手工），说清各层测试的投入产出比。

---

## 1. 前置知识

- 知道软件有「开发 → 测试 → 上线」流程
- 模块（前端/后端）会写基本功能
- 知道 bug 越晚发现修复成本越高

---

## 2. 核心概念：为什么需要体系化的测试

只靠上线前手工点一遍，问题：
- 覆盖面窄（只点了主流程，边界没点）。
- 回归成本高（每次改代码都要全点一遍）。
- 反馈慢（测出问题已经在开发完几天后）。

**测试金字塔**（经典 Mike Cohn 模型）：

```
        /\
       /E2E\      端到端（少而精，贵而慢）
      /------\
     / 集成测试 \   接口/服务间（中）
    /----------\
   /  单元测试    \  函数/类级（多，便宜，快）
  /--------------\
```

- **单测**：测最小单元（函数/方法），占比最大（~70%），快、稳、好定位。
- **集成测试**：测模块协作（如 Controller→Service→DB），占比中（~20%）。
- **端到端（E2E）**：模拟用户操作整条链路（~10%），慢、脆、贵，只覆盖核心路径。

> 反模式「冰淇淋锥」：只有大量手工 E2E、几乎没有单测——贵、慢、难维护。要避免。

### 质量左移（Shift Left）

越早发现 bug 越便宜。需求评审就考虑可测性，开发阶段写单测，而不是等测试阶段才发现。单测能在**秒级**告诉你哪里坏了。

---

## 3. 快速开始：给功能配测试策略

假设需求「用户注册接口」：
- **单测**（多）：密码强度校验函数、邮箱格式判断、各边界（空/超长/特殊字符）。快，不依赖 DB。
- **接口测试**（中）：正常注册、重复注册报错、参数缺失返回 400。用工具/脚本打接口。
- **E2E**（少）：从注册页填表到收到欢迎邮件的核心路径。
- **手工探索**：异常网络、验证码、安全（SQL 注入尝试）等难自动化部分。

## 4. 进阶用法

### 4.1 测试类型全景

| 类型 | 测什么 | 谁做 | 工具举例 |
|---|---|---|---|
| 单元测试 | 单个函数/方法 | 开发 | JUnit5 / Vitest |
| 接口测试 | API 输入输出 | 开发/测试 | Postman / Requests / REST Assured |
| 集成测试 | 多模块协作 | 开发/测试 | TestContainers / Spring Boot Test |
| 功能测试 | 功能是否符合需求 | 测试 | 手工 / 自动化 |
| 回归测试 | 改后旧功能是否还好 | 测试 | 自动化用例集 |
| 冒烟测试 | 核心路径是否通 | 测试 | 最小用例集 |
| 性能/安全测试 | 非功能 | 专项 | JMeter / 扫描器 |

### 4.2 测试左移的具体动作

- 需求评审时确认「验收标准」可量化（如「响应 < 200ms」）。
- 开发写代码同时写单测（TDD 或至少并行）。
- 提测前开发自测 + 跑单测，别把明显 bug 丢给测试。

## 5. 常见坑与排错表

| 现象 | 根因 | 解决 |
|---|---|---|
| 单测写了一堆但 bug 还多 | 只测了 happy path，边界/异常没覆盖 | 补边界、异常分支、等价类划分 |
| 全靠 E2E 自动化，跑一次半小时 | 冰淇淋锥反模式 | 把能下沉的单测/接口测试补上 |
| 改一行代码全量回归点一天 | 没自动化回归 | 沉淀回归用例集 + 接口自动化 |
| 测试环境不稳定导致 E2E 红 | 环境/数据问题非代码问题 | 环境隔离 + 测试数据自治 |
| 单测依赖数据库/网络变慢变脆 | 单测不纯 | 用 mock 隔离外部依赖 |
| 验收标准模糊（「流畅」） | 需求没量化 | 评审时定可测标准 |
| 只测功能不测异常 | 思路局限 | 异常流/边界流一并设计 |
| 自动化维护成本高放弃 | 用例太脆（强依赖 UI 文案） | 选稳定定位器、接口层自动化优先 |

## 6. 完整实战：给「优惠券核销」定测试计划

```
单测：  核销规则函数（满减计算、过期判断、叠加规则）—— 纯函数，覆盖全边界
接口：  正常核销 / 已用过 / 已过期 / 库存不足 / 并发核销
E2E：    用户领券 → 下单用券 → 实付正确
手工：   券码被篡改、超发、活动配置错误
```

**验收**：你能画出这个需求的测试金字塔分布，且单测能在本地秒级跑完给出覆盖率。

---

## 7. 最佳实践

- 遵循金字塔：多写单测、适度接口/集成、少而精的 E2E。
- 质量左移：开发中写单测，提测前自测，别把明显 bug 丢给测试。
- 单测要纯（mock 外部依赖），快且稳定才能高频跑。
- 验收标准必须可量化、可测，评审时定好。
- 回归用例集要沉淀并自动化，改代码不怕。
- E2E 只覆盖核心路径，细节交给下层测试。
