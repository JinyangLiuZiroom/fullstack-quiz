# 模块十四：三层架构与工程规范（完整学习指南）

> **学习目标**：掌握企业后端标准的「Controller / Service / Mapper」分层职责，搞清楚 DTO / VO / PO / Entity 各类对象的边界，写出结构清晰、可维护、可被同事接手的后端代码。
> **适合谁**：所有逻辑都堆在 Controller 里、或前端传什么后端就存什么、新人看不懂项目结构的同学。
> **学完能做什么**：按规范拆一个用户模块的三层，定义合理的 DTO/VO，知道哪些事该放哪一层，避免越权写入。

## 2. 核心概念：为什么分层

不分层时：Controller 里直接拼 SQL、校验、算业务、返回，一个方法 300 行，改一处崩一片。

**三层架构**（最经典）：

```
Controller 层：接收 HTTP 请求，参数校验，调 Service，包装返回
   ↓
Service 层：  业务逻辑（核心），事务边界，编排多个 Mapper
   ↓
Mapper/DAO 层：只和数据库打交道（CRUD），不含业务
```

各层只依赖下一层，禁止反向依赖（Service 不依赖 Controller，Mapper 不依赖 Service）。

### 对象分层（重要）

| 对象 | 含义 | 使用层 |
|---|---|---|
| PO / Entity | 数据库表映射（和表字段一一对应） | Mapper ↔ Service |
| DTO | 数据传输对象，接口入参/出参的契约 | Controller ↔ Service |
| VO | 给前端展示用的视图对象（按需裁剪） | Controller 返回 |
| BO | 业务对象（复杂业务中间态，可选） | Service 内部 |

> **关键原则**：**不要把 Entity 直接当接口返回给前端**。前端不该看到密码、内部状态等字段，也不该能改你没打算暴露的列。用 DTO 接收入参、用 VO/特定结构返回。

## 3. 快速开始：一个清晰的用户模块

```java
// 入参 DTO（只暴露允许前端传的字段）
@Data
public class CreateUserReq {
    @NotBlank private String name;
    @Email private String email;
}

// 出参 VO（按需裁剪，不含密码）
@Data
public class UserVO {
    private Long id;
    private String name;
    private String email;
}

// Controller：只做转发 + 校验 + 包装
@RestController
@RequestMapping("/api/users")
public class UserController {
    private final UserService service;
    public UserController(UserService service) { this.service = service; }
    @PostMapping
    public Result<Long> create(@RequestBody @Valid CreateUserReq req) {
        return Result.ok(service.create(req));
    }
    @GetMapping("/{id}")
    public Result<UserVO> get(@PathVariable Long id) {
        return Result.ok(service.getVo(id));
    }
}

// Service：业务逻辑 + 事务
@Service
public class UserService {
    private final UserMapper mapper;
    public UserService(UserMapper mapper) { this.mapper = mapper; }
    @Transactional(rollbackFor = Exception.class)
    public Long create(CreateUserReq req) {
        User u = new User();
        u.setName(req.getName()); u.setEmail(req.getEmail());
        mapper.insert(u);
        return u.getId();
    }
    public UserVO getVo(Long id) {
        User u = mapper.selectById(id);
        UserVO vo = new UserVO();   // Entity → VO 转换（用 MapStruct 更优雅）
        vo.setId(u.getId()); vo.setName(u.getName()); vo.setEmail(u.getEmail());
        return vo;
    }
}
```

## 4. 进阶用法

### 4.1 为什么 Controller 不能直接调 Mapper

- 事务边界在 Service（模块四），Controller 直接调 Mapper 无法用 `@Transactional` 统一管理。
- 业务规则（如「用户存在才能下单」）会散落各处，无法复用。
- 违反单一职责，Controller 既管 HTTP 又管业务，越来越胖。

### 4.2 转换工具

手写 Entity→VO 繁琐，用 `MapStruct`（编译期生成，无反射损耗）：

```java
@Mapper(componentModel = "spring")
public interface UserConverter {
    UserVO toVo(User user);
}
```

### 4.3 通用返回 & 异常

模块三已讲：统一 `Result<T>` + `@RestControllerAdvice`。这里强调：**Controller 不捕获业务异常**，交给全局异常处理器。

## 5. 常见坑与排错表

| 现象 | 根因 | 解决 |
|---|---|---|
| 前端改了不该改的字段（越权） | Controller 直接用 Entity 收参 | 用 DTO 只收允许字段；更新用 `updateById` 时 DTO→Entity 映射 |
| 密码出现在接口返回 | 直接返回 Entity | 返回 VO，剔除敏感字段 |
| Controller 膨胀到几百行 | 业务堆在 Controller | 抽到 Service，Controller 只转发 |
| Service 里调了 HttpServletRequest | 分层混乱 | Web 对象只在 Controller；Service 用入参 |
| 事务不生效 | 事务注解加在 Controller 或私有方法 | 加在 public Service 方法 |
| 返回结构和前端对不上 | 没用 VO 裁剪 | 定义明确 VO |
| 重复代码多 | 没抽公共 Service/Converter | 抽业务方法 + MapStruct |
| Mapper 写了业务判断 | 分层错误 | Mapper 只做数据访问，判断放 Service |

## 6. 完整实战：把「胖 Controller」重构成分层

给定一个把校验、查库、拼装、返回全写在一个方法里的 Controller，拆成：
- `CreateUserReq` DTO（带校验）
- `UserService.create`（事务、Entity 转换、业务判断）
- `UserVO`（剔除密码）
- `UserController`（只转发 + 包 Result）

**验收**：Controller 不到 30 行；Service 可单测（不依赖 HTTP）；返回不含密码；事务在 Service。

---

## 7. 最佳实践

- 严格三层：Controller（HTTP） / Service（业务+事务） / Mapper（数据）。
- 入参用 DTO、出参用 VO，**绝不直接暴露 Entity**（尤其密码、状态位）。
- 业务规则与事务放 Service，Controller 只做参数校验 + 调用 + 包装。
- 用 MapStruct 做对象转换，减少手写 getter/setter。
- 全局异常处理放 `@RestControllerAdvice`，Controller 不吞异常。
- 包结构建议：`controller / service / mapper / dto / vo / config / common`。
